// Project Walkthrough · 10
OSCAL Component Definition

A NIST OSCAL Component Definition and Profile describing the compliant-s3 Terraform module, validated with NIST's own compliance-trestle toolkit, with evidence links wired directly into signed, immutable objects already sitting in the evidence vault. Every other primitive in this toolkit proves compliance at plan time or after the fact. This is the layer that makes the whole chain machine traversable, so an assessor can follow control to component to evidence without a conversation.

oscal 1.2.1 compliance-trestle nist 800-53 terraform nist 800-53 rev 5
Problem Statement
01

The rest of this toolkit produces compliance proof at different points in time: a Terraform plan proves a resource was compliant when it was applied, a Conftest gate proves a plan was rejected or passed, a signed evidence bundle proves a specific CI run captured specific artifacts. None of that is expressed in a single, standard, machine-readable format that connects a control catalog to a profile to a component to its evidence, the way an assessor actually needs to traverse it.

OSCAL is NIST's answer: a standard format for control catalogs, profiles, components, and system security plans. This project writes the smallest real piece of that graph, one Component Definition for compliant-s3, validated end to end, with evidence links that point at real signed objects instead of placeholder URIs.

Real-World Wrinkles
03

Two things surfaced that a clean writeup would not mention. Both were about the gap between a lab's own documented assumptions and what a downstream consumer actually needs from them.

wrinkle 1 · trestle CLI
profile-resolve Moved to a Subcommand Group
The top-level trestle profile-resolve command from an older trestle release does not exist in the installed toolkit. Version 5.0.0 restructured the CLI, moving profile, catalog, component, and SSP resolution commands under a shared trestle author subcommand group. The equivalent command is trestle author profile-resolve, same flags.
wrinkle 2 · evidence vault
Evidence Link Pointed at a Bundle Whose Retention Had Already Lapsed
verify-evidence.sh passed integrity and authenticity but failed preservation: the linked bundle's Object Lock retention had expired two days after capture. The vault's retention_days default was 1, in GOVERNANCE mode, a lab-scale shortcut the module's own variable description already flagged as unfit for real evidence. Fixed by hardening the vault to 400-day COMPLIANCE-mode retention and minting a fresh signed bundle before wiring the final link.

verify-evidence.sh runs three independent checks against the linked bundle: SHA-256 integrity, Cosign authenticity against the Sigstore Rekor transparency log, and Object Lock preservation. Key Technical Decisions
05
DecisionReasoning
oscal-version 1.2.1, not the tutorial's 1.1.3trestle version reported the installed toolkit speaks 1.2.1. Catalog, profile, and component all have to share one OSCAL version, so the installed version wins over any older example.
Catalog source pinned to main, not a version tagTested both. main resolved, a candidate tag path did not. Accepted the drift risk main carries rather than spend more effort guessing the right tag.
Fixed the vault's retention instead of shipping a broken evidence linkAn evidence link that fails its own preservation check within days undercuts the entire premise that the audit becomes a graph traversal.
lock_mode COMPLIANCE, retention_days 400Matches the module's own documented guidance for real evidence. Confirmed before applying, since COMPLIANCE mode cannot be reversed on anything uploaded under it.
AU-3 evidence cited from the bundle's plan.json, no dedicated policy gate yetThe CI pipeline gates SC-28, AC-3, and CM-6 today. AU-3 is not policy-enforced yet, documented as a known limitation rather than implying coverage that does not exist.
