// Project Walkthrough · 09
GCP Security Services Baseline

A Terraform baseline that stands up GCP's project-level compliance backbone: three Org Policy constraints enforced in REJECT mode at the API layer, a repo-scoped Workload Identity Federation pool for keyless CI authentication, and Data Access audit logging turned on for the services this toolkit actually touches. The GCP mirror of the AWS security baseline, applied by hand, evidence signed and vaulted into the same cross-cloud evidence vault.

terraform gcp org policy workload identity federation cloud audit logs nist 800-53 rev 5 · fedramp moderate
Problem Statement
01

The AWS baseline proved that account-level compliance backbone (CloudTrail, Security Hub) is a different altitude from per-resource Terraform primitives like compliant-s3. GCP needs the same backbone, but its controls live in different places entirely: Org Policy constraints instead of account settings, Workload Identity Federation instead of OIDC-to-role trust, and Cloud Audit Logs Data Access entries that are off by default, one of the most commonly cited GCP audit gaps.

This baseline enforces three of those constraints at the API layer, so a non-compliant change is rejected before it lands, not caught after the fact in a scheduled scan.

What It Deploys
02
// CM-6 / AC-2 / AC-3
Org Policy REJECT Enforcement
Three constraints in REJECT mode: uniform bucket-level access, no new service account keys, mandatory OS Login. Enforced by the GCP API on every future action, not a convention someone has to remember.
// IA-2(6) / IA-8
Repo-Scoped Workload Identity Federation
A WIF pool with attribute_condition locked to one exact GitHub repository string. CI authenticates keyless. No other public repo can mint a token that impersonates this identity.
// AU-3 / AU-12
Data Access Audit Logs
Turned on for the three GCP services this toolkit actually touches. Off by default on GCP, which makes it the audit gap most likely to be missed in a real environment.
// cross-cloud
Same Vault, Second Cloud
Signed with the same Cosign pattern and uploaded to the same evidence vault as the AWS baseline. One evidence chain, two cloud providers.
Real-World Wrinkles
03

Three stacked wrinkles surfaced during the apply, each one hiding behind a misleading error message from the layer above it.

wrinkle 1 · provider config
Misleading "API Disabled" 403 That Wasn't About a Disabled API
Org Policy resources failed with a SERVICE_DISABLED 403 pointing at a consumer project number that did not match the real target project. The google Terraform provider does not automatically forward ADC's quota project to every API call. Fixed with user_project_override = true plus an explicit billing_project, which stopped requests from silently falling back to an unrelated Google-internal default project.
wrinkle 2 · main.tf
Resource Manager API Never Enabled on This Project
The Lab 2.4 GCS module never called cloudresourcemanager.googleapis.com, so this baseline was the first thing in the project's history to need it. A real, previously invisible gap, not a flake. Enabled once and it stayed fixed.
wrinkle 3 · org_policy.tf
Project-Level Owner Did Not Include Permission to Create Org Policies
Three google_org_policy_policy resources failed with orgpolicy.policies.create permission denied, despite the identity holding roles/owner on the project. roles/orgpolicy.policyAdmin is not grantable at the project level on this resource type. gcloud projects describe --format="value(parent.type,parent.id)" confirmed the project sits inside a real GCP Organization, which is what made an organization-level grant of roles/orgpolicy.policyAdmin both necessary and possible.

Key Technical Decisions
05
DecisionReasoning
Modern google_org_policy_policy, not the legacy resourceThe legacy resource's boolean_policy block does not match how the constraint is actually expressed in current GCP APIs. The modern resource's spec.rules.enforce string is the real current shape.
user_project_override plus explicit billing_projectWithout it, ADC's quota project is not applied to every API call, and the resulting 403 reads exactly like the target project's API is disabled when it never was.
attribute_condition scoped to one exact GitHub repo stringWithout it, any public GitHub repository could mint an OIDC token that impersonates the CI service account.
WIF service account holds only roles/viewer, no key ever createdThis same baseline's own Org Policy blocks any service account key project-wide going forward. The design has to be keyless by construction, not by convention.
No labels block anywhere in this baselineOrg Policy, WIF, and audit config are IAM and policy control-plane objects. GCP does not support labels on any of them, a break from the tag-every-resource convention used elsewhere in the toolkit.
Org-level orgpolicy.policyAdmin grant, not a project-level workaroundConfirmed the project has a real parent Organization before granting anything at that altitude, since an org-level IAM change carries materially more blast radius than a project-level one.
